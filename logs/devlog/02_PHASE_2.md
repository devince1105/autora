## T-201 · 工作執行資料表與生命週期（遷移 0004）

### 做了什麼
- 資料表（`db/models/tasks.py`）：
  - `workflow_runs`：一次工作流程範本的實例，屬於某個專案；
  - `tasks`：原子工作單位，含 `required_role`、`depends_on`、`attempt`/`max_attempts`、`budget_usd`、`progress`、`priority`、租約欄位；
  - `agent_runs`：一次代理執行，含輸入輸出、評估結果、下游交接、錯誤、成本與權杖用量；
  - `agent_steps`：執行中的每一步（思考、行動、觀察、評估、修補），完整內容放物件儲存（T-210）。
- `projects.created_by_run_id` 補上外鍵，指向提出該專案的代理執行（Phase 1 時資料表尚不存在）。
- 生命週期狀態機（`runtime/lifecycles.py`）：`TASK_FSM`、`AGENT_RUN_FSM`、`WORKFLOW_RUN_FSM`。後續的任務管理員、工作流程圖、審批與代理執行器都必須透過它們改變狀態，因此每次轉換都有驗證與稽核紀錄。

### 由資料庫保證的規則
| 規則 | 理由 |
|---|---|
| 任務「正在執行」若且唯若持有租約（`lease_owner` 與 `lease_until` 同時存在） | 任務管理員若忘了釋放或忘了取得租約，寫入時就會失敗，不會留下幽靈租約或無主的執行中任務 |
| 代理執行處於終止狀態若且唯若有 `finished_at` | 避免「看起來還在跑、其實已結束」的資料 |
| 每個（任務、嘗試次數）只能有一筆代理執行 | 重試不會產生重複執行 |
| `attempt` 介於 0 與 `max_attempts` 之間 | 重試上限由資料庫擋住 |
| `agent_steps` 只能新增 | 執行軌跡是稽核資料，不可改寫（沿用 0002 的觸發器函式） |
| 名稱格式檢查（任務名稱、角色、範本名稱） | 與事件、佈局使用的識別字一致 |

索引依實際查詢設計：
- 工作程序領取任務：`(company_id, priority, created_at) WHERE state = 'READY'`；
- 回收過期租約：`(lease_until) WHERE state = 'RUNNING'`。

### 狀態機設計決策
- **失敗重試不經過 FAILED**：可重試的失敗走「執行中 → 就緒」（嘗試次數由任務管理員遞增），FAILED 只代表最終失敗；租約過期也走「執行中 → 就緒」。
- **審批會釋放工作程序**：代理任務走「執行中 → 等待審批 → 就緒」，核准後由工作程序重新領取並恢復同一個代理執行；人工或服務節點則是「就緒 → 等待審批 → 成功」。
- **代理執行必須先評估才能完成**：「執行中 → 已完成」不允許，必須經過「評估中」。
- 以測試保證三個狀態機的結構性質：每個狀態都能從初始狀態到達；每個狀態都能到達終止狀態（不會卡住）；每個非終止狀態都能被取消或中止。

### 遇到的問題
- （我造成的）又使用了不存在的 `mapped_column(type_=...)` 與 `Base.registry.type_annotation_map` 寫法，匯入時即失敗，改為 `mapped_column(JSONB)`。
- （我造成的）步驟測試在唯一性檢查後回滾，連帶把先前新增的步驟也回滾，導致後續的「只能新增」檢查修改 0 列、觸發器沒有觸發而誤判。與階段 1 的同類問題相同；改為拆成獨立測試。**教訓：在同一測試中，任何 `session.rollback()` 之後都不能假設先前寫入的資料仍存在。**

### 驗證
- `make migrate`、`make db-check`（模型與遷移一致）、降版到 0003 再升版成功。
- `tests/db/test_task_models.py`、`tests/runtime/test_lifecycles.py`；全部 Python 測試 **173 個通過**（`AUTORA_REQUIRE_DB=1`）。

## T-212 · 排程器（遷移 0005）

### 做了什麼
- `schedules` 資料表：cron 表達式、時區、處理器名稱、下次執行時間、租約、最近錯誤與連續失敗次數。
- `runtime/scheduler.py`：每次 tick 領取到期排程（`FOR UPDATE SKIP LOCKED` 加租約），在同一個交易中執行處理器、推進下次執行時間、寫入 `SCHEDULE_FIRED`、清除租約。

### 與設計不同：不使用 APScheduler
- 技術選型原本寫 APScheduler。但 `schedules` 資料表本身已保存下次執行時間與租約；APScheduler 的記憶體排程會變成第二份狀態，可能與資料表不一致。
- 改為直接輪詢資料表，機制與任務佇列相同：多個工作程序天然互斥，重啟不遺失，也不需要額外協調。cron 解析使用 `croniter`。已在 `platform/13` 技術選型表加註。

### 語意
- **同一時間點只觸發一次**：4 個工作程序同時 tick，處理器只被呼叫一次（有測試）。
- **處理器失敗**：處理器的寫入全部回滾，下次執行時間不推進；保留租約到「現在 + 重試間隔」，避免每次 tick 都重試；記錄錯誤訊息與連續失敗次數。
- **錯過的執行會合併**：停機三天後恢復，只補觸發一次，接著回到正常節奏，不會一次補跑三天份。
- **當機的工作程序**：租約過期後由其他工作程序接手。
- 時區以排程自己的時區計算（例如台北 06:00 = UTC 前一天 22:00，有測試）。

### 驗證
`tests/runtime/test_scheduler.py`：11 個通過。

## T-204 · 工具登錄表與工具事件

### 做了什麼
- `runtime/tools/registry.py`：以裝飾器註冊工具；工具是 `async fn(args: 模型, ctx) -> ToolResult`，註冊時宣告副作用等級（read / write / irreversible）、逾時與是否可重試。
- `invoke()`：驗證參數 → 寫入 `TOOL_CALLED` → 在逾時限制內執行 → 寫入 `TOOL_COMPLETED`（含產出物 `produced`、成本）或 `TOOL_FAILED`。每次呼叫必定成對。

### 關鍵決策：拆成三個交易
- `emit()` 會持有該公司的事件鎖直到提交。若 `TOOL_CALLED` 與一個 30 秒的網頁抓取在同一個交易，這段期間同公司所有事件寫入都會被卡住。
- 因此：
  1. `TOOL_CALLED` 單獨提交（可附帶 `before_call`，讓代理執行器把「活動狀態 = 工作中」與它一起提交）；
  2. 工具在第二個交易執行，**工具的領域寫入與 `TOOL_COMPLETED` 一起提交**（例如證據資料列與事件要嘛都存在，要嘛都不存在）；
  3. 失敗時回滾第二個交易，另外提交 `TOOL_FAILED`。
- 有測試證明：工具執行期間，其他寫入者可以為同一公司寫入事件。

### 其他
- 參數驗證失敗、逾時、例外都會記錄為 `TOOL_FAILED`（先有 `TOOL_CALLED`），不會拋出；未註冊的工具會拋出 `UnknownTool`，因為沒有副作用等級可以記錄。
- 每次呼叫提供穩定的冪等鍵（範圍 + 步驟序號 + 工具名 + 參數雜湊），重試時不變，寫入型工具必須用它避免重複寫入。
- 政策判斷（允許 / 拒絕 / 需審批）不在登錄表內，由 T-205 政策引擎在呼叫前決定。

### 驗證
`tests/runtime/test_tools.py`：11 個通過。

## T-210 · 執行軌跡與物件儲存

### 做了什麼
- `infra/blobstore.py`：物件儲存介面與本機檔案實作。寫入為原子操作（暫存檔 + rename）；物件鍵只允許安全字元，不可能跳出根目錄。
- `runtime/trace/recorder.py`：`record_step()` 以代理執行資料列鎖定取得下一個序號，完整的提示與回應寫入物件儲存，資料表只存鍵。先寫物件再寫資料列：交易回滾只會留下無人引用的物件（無害），反過來則可能出現指向不存在物件的資料列。
- `runtime/trace/query.py`：`get_run_trace()` 回傳該執行的真實事件（依 `seq`），並以負載中的 `step_seq` 接上對應步驟；沒有事件引用的步驟也會列出。軌跡中沒有任何合成的資料。
- API：`GET /api/runs/{id}/trace`、`GET /api/runs/{id}/steps/{seq}/blob`（完整內容只從後者取得，有測試確認軌跡 API 不會洩漏提示原文）。

### 與設計不同：S3 延後
- 規格要求本機與 S3 兩種實作。目前沒有任何功能需要 S3，而 S3 的正確測試需要額外的 MinIO 服務。
- 已建立介面與共用的契約測試套件（`tests/infra/test_blobstore.py`）；之後加入 S3 時，只需讓它通過同一套測試。

### 遇到的問題
- （我造成的）把 API 測試放在 `tests/runtime`，但 `api` 測試夾具定義在 `tests/api/conftest.py`，因此找不到；一度用 `api._transport.app` 這種取巧寫法。改為把 API 測試移到 `tests/api/`，並由夾具正式覆寫物件儲存依賴。
- （我造成的）寫了一個沒有檢查任何東西的測試（`test_agent_step_model_is_imported`），已刪除。

### 驗證

## T-209 · 成本守門員（遷移 0007）

### 做了什麼
- `runtime/cost/guard.py`：每次模型呼叫前檢查四層預算，任何一層超出就拒絕，並寫入 `BUDGET_EXHAUSTED` 事件（即使呼叫沒有發生，事件也會提交）。

| 層級 | 上限來源 | 計入的花費 |
|---|---|---|
| 執行 | 代理的 `budget.per_run_usd` | 此執行的模型呼叫 |
| 任務 | `tasks.budget_usd` | 此任務所有執行的模型呼叫 |
| 專案 | 該專案的硬上限預算（日 / 月） | 該專案在期間內的呼叫 |
| 公司 | 沒有指定專案的硬上限預算 | 全公司在期間內的呼叫 |

- 花費 = 已記錄的 `model_calls` 成本 + 進行中呼叫的預留金額（`cost_reservations` 資料表）。
- 預留在每間公司一把的交易諮詢鎖內完成：**5 個並行請求搶只夠一次的預算，恰好 1 個成功、4 個被拒**（有測試）。
- 預留超過 15 分鐘未結算視為過期，不再計入，避免當機的工作程序永久占用預算。
- 成功呼叫在寫入 `model_calls` 的同一交易中結算預留（連結呼叫、記錄實際成本）；失敗呼叫則釋放預留。

### 與設計不同或需要注意之處
- **`BUDGET_EXHAUSTED` 從公司層移到執行環境層**：由執行環境的成本守門員觸發，而執行環境不可匯入公司層（import-linter 會擋）。事件結構已重新產生，並回寫 `3d-office/03 §8`。
- **估算刻意偏高**：輸入權杖以「字元數 / 4」估算，輸出以完整的 `max_output_tokens` 計。
- **「週期」預算暫時以「日」計算**：週期資料表尚未建立，而 MVP 的週期就是每天。
- **軟上限（`hard_cap = false`）不在此擋下**，留給報表使用。
- **目前只計模型成本**：工具成本等工具用量寫入帳本後再納入。

### 遇到的問題
- （我造成的）在測試中再次使用 `__import__` 取巧寫法，已改為正常匯入。
- （我造成的）移除未使用欄位 `company_wide` 時，替換字串因格式化而對不上導致失敗，但串接的指令仍印出「已移除」。之後確認實際未移除並重新處理。**教訓：修改檔案的指令不要用 `;` 串接成功訊息，要以實際檢查結果為準。**

### 驗證
`tests/runtime/test_cost_guard.py`：12 個通過（包括被拒的呼叫完全不會到達模型供應者、也不會產生呼叫紀錄）。

## T-202 · 任務管理員（遷移 0008）

### 做了什麼
- `runtime/task_manager.py`：`tasks` 資料表就是佇列。工作程序以 `FOR UPDATE SKIP LOCKED` 領取任務並持有租約；每次狀態變更都經過 `TASK_FSM` / `AGENT_RUN_FSM`（有稽核）並在呼叫端的交易內發出事件。所有方法都不自行提交：任務變更、事件與代理活動狀態要嘛一起落地，要嘛全部不落地。
- 操作：`add_task`、`mark_ready`、`claim_next`、`heartbeat`、`succeed`、`fail`、`abort`（預算 / 政策 / 人為）、`cancel`、`release_blocked`、`reap_expired_leases`。
- 依賴傳播（哪些下游任務變為就緒、上游最終失敗時取消哪些下游）留給 T-203，透過 `on_task_finished` / `on_task_failed` 兩個掛鉤接入。

### 讓佇列誠實的規則
| 規則 | 做法 |
|---|---|
| **一次領取一個令牌** | 領取時產生令牌寫在任務上；租約被回收後，原工作程序再試圖完成任務會得到 `LeaseLost`，不會覆寫任何資料。只有回收器能收回租約 |
| **每個代理同時只有一個未完成的執行** | 資料庫部分唯一索引 `uq_agent_runs_open_per_agent`。代理是一個人，只能有一個目前狀態 |
| **領取即消耗一次嘗試** | 當機也算一次（有毒任務不能無限次弄垮工作程序）；預算受阻也算（該次執行的資料列已存在，嘗試編號無法重用），`release_blocked` 對用完嘗試次數的任務直接判定最終失敗 |
| **重試有退避** | 新欄位 `available_at` = 現在 + 10 秒 × 2^(嘗試次數−1)，上限 5 分鐘 |
| **FAILED 只代表最終失敗** | 可重試的失敗回到 READY；租約過期也回到 READY |
| **佇列以公司為範圍** | 領取查詢一律以代理所屬公司過濾（有測試：另一家公司的同角色代理領不到） |
| **等待審批的執行會被延續** | 領取時若該（任務, 嘗試次數）已有未完成的執行，沿用它而不是開新嘗試（T-206 使用） |

### 活動狀態的對應
- 建立有依賴的 PENDING 任務時，該角色中閒置的代理進入 WAITING{upstream}，並記錄在等哪些角色。
- 成功 → COMPLETED（含交接對象）；最終失敗 → FAILED；預算受阻 → WAITING{budget}；可重試的失敗、租約回收、任務取消 → IDLE（新增 `AGENT_IDLE{reason: run_ended}`）。非最終的 `AGENT_RUN_FAILED` / `AGENT_RUN_ABORTED` 仍寫入事件供軌跡使用，但不改變活動狀態。

### 遇到的問題與修正
- Alembic 的自動產生不會比對 CHECK 約束：`lease_iff_running` 改為也要求令牌，必須手寫進遷移 0008。第一版寫法讓命名慣例套用兩次（`ck_tasks_ck_tasks_…`），降版失敗後改為 `op.f()` 搭配裸名稱。
- （我造成的）`succeed` / `fail` 直接把執行推到終止狀態，但執行狀態機要求經過中間狀態。解法是在通用狀態機加入 `shortest_path` / `transition_via`，任務管理員只補完剩餘的合法路徑（每一步都有稽核）。
- 接著資料庫的 `finished_iff_terminal` 又擋下一個真實錯誤：我在走中間狀態之前就設定了 `finished_at`。改為非終止的跳轉先走，`finished_at` 與最後一跳一起寫入。
- 原本設計「預算受阻退還嘗試次數」，但同一（任務, 嘗試次數）的執行資料列已存在，重新領取時違反唯一約束。改為統一「領取即消耗」，並補上 `BLOCKED_BUDGET → FAILED` 的狀態機邊。**教訓：三個錯誤都是資料庫約束先抓到的，證明 T-201 把不變式放在資料庫層是對的。**
