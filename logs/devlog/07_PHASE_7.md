## T-701 · 價格、訂閱、付款

### 開工前的盤點：九張表裡已經有三張

任務清單寫的是 products、customers、leads、opportunities、subscriptions、orders、payments、campaigns、campaign_spend 九張表。這份清單是營收模型還沒決定時寫的，所以把每一種可能都列了進去。對照現況：

| 表 | 現況 | 這次 |
|---|---|---|
| `products` | T-600 已做（組織 v2） | 不動 |
| `customers` | T-612 已做（D-018） | 不動，由訂閱呼叫 |
| `opportunities` | T-611 已做，而且意思不一樣：那裡是「可能成為一門生意的機會」，不是銷售漏斗裡的商機 | 不動 |
| `subscriptions`、`payments` | 沒有 | **新增** |
| （清單外）`prices` | 沒有 | **新增**。理由見下 |
| `leads` | 沒有 | **不做**：訂閱站的 lead 就是一個 email，而這家公司不存個資（D-018） |
| `orders` | 沒有 | **不做**：沒有一次性商品 |
| `campaigns`、`campaign_spend` | 沒有 | **不做**：只用自有網站，沒有付費廣告。T-703 一起延後 |

**為什麼另外加 `prices`，而不是在 `products` 加一個價格欄位**：價格會變，產品不會。月費從 5 塊調到 6 塊時，舊訂閱仍然是用 5 塊賣出去的，它的付款也是 5 塊。所以價格是一張表：調價就是把舊的一列退休、新增一列，每個訂閱都指向它當初成交的那個價格。這也是 Stripe 自己的模型（Product 跟 Price 分開），T-702 對應起來是一對一。

### 放在哪一層：`company/`，不是 `domains/business/`

路線圖原本寫 `autora/domains/business/**`。改放 `company/subscriptions.py`，理由跟 D-018 把 `customers` 放在 company 一樣：**每種產業收錢的方式都一樣**。新聞媒體、教育、SaaS 的訂閱，都是「一個價格、一個週期、金流商說錢到了」。`test_core_vocabulary` 照樣全綠，這一層沒有出現任何領域詞彙。

**Stripe 在核心裡只是一個字串**：`provider = 'stripe'`，資料庫檢查它的格式（`^[a-z][a-z0-9_]*$`），但沒有任何程式寫 `if provider == "stripe"`。Stripe 的 SDK、webhook 簽章、事件名稱對應，全部是 T-702 adapter 的事。

### 三條規則

1. **每個寫入都以金流商的 id 做冪等。** 金流商一定會重送同一個事件，第二次送達不能造成任何改變：不會多一個訂閱、多一筆付款，也不會多一列帳本。訂閱靠 `(company_id, provider, external_ref)` 唯一；付款靠 `(provider, external_ref)` 唯一，對應的帳本列的冪等鍵是 `payment:{provider}:{external_ref}`。
2. **訂閱是承諾，付款才是錢。** 只有 `record_payment` 會寫帳本。訂閱變成 ACTIVE 不會入帳，因為那只代表金流商準備去扣款，扣成功了才有收入。帳本記的是**實際扣到的金額**，不是牌價（proration、折扣都會讓兩者不同）。
3. **不存個資**，延續 D-018。三張表都只有金流商的 id 和金額。測試會掃欄位名稱，出現 name、email、card 之類的字就會紅。

### 狀態機

```
TRIALING → ACTIVE | PAST_DUE | CANCELED
ACTIVE   → PAST_DUE | CANCELED
PAST_DUE → ACTIVE | CANCELED
CANCELED   （終點）
```

- **PAST_DUE 可以回到 ACTIVE**：卡片扣款失敗後金流商會重試，重試成功就回來了。PAST_DUE 仍然算「付費中」，因為多數重試會成功。
- **CANCELED 是終點**：同一個人回來訂閱，是一筆新的訂閱。舊的那筆仍然記得他什麼時候離開。
- **同一個狀態再送一次不算轉移**，只更新 `current_period_end`。金流商的 `subscription.updated` 事件大多是這種。
- **取消客戶的最後一個訂閱，就等於客戶流失**：呼叫 `customers.churn`。如果他還有另一個訂閱沒取消，就不算流失。

### 付款只能新增

`payments` 掛上 migration 0002 的那個 `autora_forbid_mutation()` trigger，跟 `transactions` 一樣。退款會是另一列，不會去改原來那一列。

### 一個刻意拒絕、不去猜的情況

如果帳本裡已經有 `payment:stripe:in_xxx` 這個鍵，卻沒有任何一筆付款指向它，代表有人手動寫過帳本。這時兩條路都不對：安靜地回傳會把這筆付款弄丟，另外再寫一列又會被唯一鍵擋下。所以直接丟出錯誤，說明原因（`test_a_ledger_row_with_no_payment_behind_it_is_refused_not_guessed`）。

### 附帶的小改動

`Ledger.record` 多了 `product_id` 參數。`transactions.product_id` 這個欄位在 T-600 就有了，但一直沒有寫入的路徑，所以「每個產品賺多少」到今天之前一直答不出來。

### 自己寫錯、修掉的

- 第一版測試用了 `Ledger().revenue()`，但這個方法不存在。帳本只有 `balance()`，改用它（這些測試的公司只有收入，所以 balance 就等於收入）。
- `pytest.raises` 包在 `begin_nested()` 裡面，順序寫反了：例外被 `pytest.raises` 接住之後，savepoint 以為一切正常而嘗試 RELEASE，結果在已經中止的交易上失敗。改成 `pytest.raises` 在外、savepoint 在內。
- 稽核列用 `created_at` 排序，但 `state_transitions` 沒有這個欄位，時間欄位叫 `at`。而且 `at` 是 `now()`，同一個交易裡兩列的值會一樣，所以改用 id 排序（uuid7 本身就是依寫入時間排序）。
- 刪掉一個自己寫的測試：它檢查「enum 的每個值都在 CHECK 約束裡」，但約束本來就是從 enum 產生的，這個測試永遠不會失敗。
- `test_company_catalog_complete` 紅了一次，這是預期中的：它是事件目錄的絆線，新增事件時必須同步更新清單。已經更新清單，也更新了 `11_EVENT_CATALOG.md`（新增 Revenue 群組；PAYMENT_RECEIVED 不再「移至 Business 群組」）。

### 留給 T-702 的

- **回頭客**：`customers.acquire` 遇到已經流失的客戶，會直接回傳那一列，`churned_at` 還在。同一個人流失之後又回來訂閱，`paying()` 不會算到他。要不要「復活」一個客戶（還是把回頭客當成新的一列），要等看到 Stripe 實際送來的資料再決定。

## 方向調整（2026-09-22）：Stripe 不能用

T-701 推上去之後，使用者告知**台灣的銀行帳戶不支援 Stripe**。接下來的對話做了三個決定：

1. **金流改用統一金流（PAYUNi）**。綠界的審核太麻煩；統一金流的個人會員可以申請（信用卡額度每月 20 萬、撥款 T+7）。先用個人身分收款，營運金額超過一定程度再轉成公司。
2. **不做定期扣款，改成一次付款買一年使用權**。我原本查到統一金流的定期扣款要另外申請幕後授權和信用卡 Token，還在規劃「由我們的系統每期發動扣款」。使用者指出這樣太繞了：只要收一次款，給一年的使用權就好。這樣連額外權限都不用申請，信用卡、ATM、超商代碼都能收。
3. **讀者用 Email 登入**。「給對方一年使用權」的前提是網站認得這個人，但公開站目前不用登入（T-515），系統也不存個資（D-018）。有兩種做法：Email 登入連結，或完全不存個資的兌換碼。使用者選了 Email 登入。

另外，統一金流只收新台幣，所以要先處理**幣別**。

**T-701 已經做好的部分沒有白費**：金流商在程式裡只是一個字串，三張表、付款冪等、只能新增不能修改、不存個資這些都照樣適用。要改的是「訂閱」的語意（見下一批）。

## D-023 · 新台幣為主幣別

### 問題

帳本、預算、報表、CEO 看到的數字、審批門檻全部是美元（寫死的）。統一金流收進來的是新台幣。兩種幣別放進同一張表直接加總，餘額就會是錯的。

### 設計：兩種錢分開，帳本只有一種幣別

盤點之後，系統裡的「錢」其實有兩種：

| | 是什麼 | 幣別 |
|---|---|---|
| **計量** | 每一次模型呼叫、搜尋花了多少；每次執行、每個任務的上限；預留 | **維持美元**。供應商就是用美元收費，這是事實，換算只會多一層誤差 |
| **公司的錢** | 帳本、預算、收入、報表、Dashboard、CEO 的快照、審批門檻 | **新台幣** |

兩者交會的地方各自只有一個轉換點，全部經過 `infra/money.py`：

- **帳本**：`Ledger.record` 是唯一的入口。非主幣別的金額在這裡換算，並在同一列記下 `source_amount`、`source_currency`、`fx_rate`。每天結算模型費用時傳入 `currency="USD"`，由這裡換成新台幣。
- **報表**：把計量的美元換成新台幣再加總（Reporting、Dashboard KPI）。
- **成本守門員**：預算是新台幣，花費是美元。**移動的是預算**：預算只是一個數字，花費卻是很多筆。

放在 infra 層，是因為 runtime 的守門員和 company 層都要用，而 runtime 不能 import company。

### 匯率

先用設定檔裡的固定值 `FX_RATES={"USD":"32"}`，手動更新。每一列都記著自己當時用的匯率，所以之後改匯率或接台銀的每日匯率，都不會改寫過去的帳。遇到沒有匯率的幣別時直接拒絕（`FxError`），不會用猜的。

### 改名

指標名稱不再帶幣別：`cost_usd` → `cost`，`revenue_usd` → `revenue`，`profit_usd` → `profit`，`model_cost_usd` → `model_cost`，單位就是主幣別。`views_per_usd` → `views_per_cost_unit`。policy 的 `governance.*_limit_usd` 拿掉 `_usd`。名稱如果寫著 usd，值卻是新台幣，那個名稱就是在說謊。

計量的欄位（`model_calls.cost_usd`、`tasks.budget_usd`、`per_run_usd`）**名稱不變**，因為它們確實是美元。

### 預設值照 32 換算

CEO 撥款門檻 $5 → NT$160、探索上限 $2 → NT$64、擴大事業 $50 → NT$1600、模擬預設撥款 NT$160。行為跟改之前完全一樣，只是單位換了。這些值使用者之後可以調。

### 既有資料（migration 0036）

用 32 一次換算：交易（保留原始美元和匯率；因為 append-only，只在這一個語句期間暫停 trigger，做完馬上恢復）、預算、KPI 快照、停損條件、目標、policy。降級可以完整還原。

**不換算的**：
- 計量表：本來就是美元。
- 付款與價格：記的是金流商實際收的幣別。
- 凍結的提案：核准指向的是當時那份文件。
- cycle 的計畫與覆盤：那天寫下的內容。

驗證：另外開一個暫時的資料庫，塞入一組美元樣本（交易、預算、policy、停損條件、KPI 快照、目標），跑升級 → 檢查 → 降級 → 檢查 → 再升級。1.5 美元 → 48 新台幣（`source_amount` 1.5、`fx_rate` 32）；預算 10 → 320；門檻 50 → 1600；`cost_usd > 2` → `cost > 64`；`views_per_usd < 20` → `views_per_cost_unit < 0.625`。降級後全部回到原值。暫時的資料庫已經刪除。

### 畫面

Dashboard 本來就用 `Intl.NumberFormat` 並帶入 API 回傳的幣別，所以不用改。在 zh-TW 語系下，新台幣顯示為「$87.50」，美元顯示為「US$87.50」。Cycle 列表原本寫死「US$」，改為依幣別格式化。代理面板和 trace 裡每次執行的成本本來就是計量，維持「US$」。給代理看的文字（命令摘要、每日摘要）用 `format_money` 輸出「NT$160」。CEO 的提示多加一句：所有金額都是快照裡 `capital.currency` 的幣別。

### 測試怎麼改（重點：沒有東西壞掉，改的是測試的單位）

完整測試第一次跑出 29 個失敗，每一個都是「測試假設帳本和報表是美元」，沒有一個是換算寫錯。逐一處理的方式：

| 測試 | 改法 |
|---|---|
| `test_ledger` | 用固定的 `Fx(TWD, USD=32)`。結算的列是新台幣，並檢查 `source_amount`、`fx_rate`。P-7 改成「計量的美元 == 帳本各列 `source_amount` 的總和」，另外驗證新台幣總額 == Σ(原始金額 × 該列匯率)。 |
| `test_reporting` | 第一個測試用 32，驗證換算（$0.50 → NT$16）。其餘測試關心的是「哪些呼叫算進哪個範圍」，用 1:1 匯率保留原本的算術，並在檔頭說明原因。 |
| `test_cost_guard` | 預算改寫成新台幣（3.20 = $0.10），行為與原本相同。 |
| policy、預算閘門驗收、Dashboard KPI、治理、摘要、新聞室比率、cycles API | 數字改成新台幣，並註明原本的美元值。 |

新增的測試：
- 主幣別的錢照原樣入帳。
- 之後改匯率，不會改寫已經入帳的列。
- 沒有匯率的幣別會被拒絕。
- **守門員比較的是金額、不是數字**：NT$1.50 這個數字比一次 $0.05 的呼叫大，但實際上是比較少的錢，必須擋下；NT$2.00 = $0.0625 則放行。
- Cycle 列表以新台幣顯示。

- 完整 Python 測試：1400 個通過。
- web 312 個（Cycle 列表的測試多了一條檢查）、event-schema 8 個通過。

## D-024 · T-701 改成一年使用權

### 改了什麼

「訂閱」在 T-701 裡是 Stripe 那一邊的物件：它有自己的 id、自己的狀態（試用、付費中、逾期、取消），也由它負責按期扣款。改成單次付款之後，金流商那邊沒有任何「訂閱」可以對應，這張表就失去了意義。所以換成**使用權**（`memberships`）：

| | 之前（D-022） | 現在（D-024） |
|---|---|---|
| 是什麼 | 金流商的訂閱物件在我們這邊的副本 | 我們自己的紀錄：誰可以看哪個產品、看到什麼時候 |
| 狀態 | TRIALING / ACTIVE / PAST_DUE / CANCELED | ACTIVE / EXPIRED |
| 誰改變它 | 金流商的通知 | 付款（延長）與時間（到期） |
| 一筆付款買到什麼 | 沒有記錄 | 付款上記 `grants_from` → `grants_until` |
| 價格 | 有金流商的 id | 我們自己的，下單時帶出去 |

一個客戶對一個產品只有**一列**使用權：續購時延長這一列，過期後回來時重新打開這一列。每一段時間是由哪一筆付款買的，記在付款上。

### 規則

- **提早續購不會浪費**：還沒到期就付款，新的一年從原本的到期日往後接。例如 6 月付款、9 月才到期，新的一年從 9 月開始算。
- **過期後才買，從付款那天起算**，不會往回補。
- **能不能看，看的是日期**（`expires_at > now`），在讀者請求的當下判斷。EXPIRED 是每天由 cycle 寫一次的帳務紀錄，所以就算那天的結算還沒跑，時間一到也看不了（`test_access_ends_on_time_even_before_the_books_catch_up`）。
- **到期處理掛在「進入 MEASURING」時，排在帳本與報表之前**，所以報表算付費人數時，今天到期的人已經流失了。
- **到期不一定是流失**：如果客戶還有別的產品在有效期內，就不算流失。
- **流失的時間點是到期那一刻**，不是系統發現的那一刻。
- **回頭客**：重開同一個客戶（`customers.reactivate`，發出 CUSTOMER_RETURNED 並記錄離開幾天），不會新增一個客戶，所以 CUSTOMER_ACQUIRED 仍然只有一次。**已知代價**：`churned_at` 會被清掉，所以查詢空窗期內某個時間點的 `paying(at=...)`，會把他算成付費中。空窗期本身仍然記在事件和每筆付款的期間裡，哪天報表需要再從那裡算。
- 一年的算法是「明年的同一天」。2/29 買的，到期日是隔年的 2/28；月費在 1/31 購買，到期日是 2/28。
- 入帳類別從 `subscription` 改成 `membership`。

### migration 0037

- 付款表：拿掉 `subscription_id`，加上 `price_id`、`membership_id`、`grants_from`、`grants_until`，以及一條約束：「買了使用權，就要說清楚是哪一段」。

## D-025 · 讀者 Email 登入與會員專屬文章

使用者的四個決定：大部分文章免費、部分會員專屬；年費 NT$360；登入信用 Resend 寄；`.env` 先放好統一金流的設定鍵。

### 讀者資料自成一層

「給對方一年使用權」的前提是網站認得這個人，所以系統第一次要存 email。這跟 D-018「代理讀得到的地方沒有個資」正面衝突，解法是**把讀者放進自己的一層**：

- 新套件 `autora/accounts/`，位置在 `domains` 同層（app 之下）。
- `.importlinter` 新增一條契約：**`company`、`domains`、`runtime`、`db` 都不准 import `autora.accounts`**。代理、新聞室、公司層沒有任何路徑可以讀到 email。

三張表（migration 0038）：`readers`（email、最後出現時間）、`login_tokens`、`reader_sessions`。**兩種 token 都只存 SHA-256 雜湊**：資料庫被拿走，也不能拿來登入。

### 登入

沒有密碼：輸入 email → 寄一次性連結（15 分鐘、只能用一次）→ 建立 cookie。

- **要求連結時一律回同樣的答案**，不管這個 email 有沒有帳號。否則這個表單就變成「查詢誰是這裡的讀者」的工具。
- 連結失效的三種情況（沒這個 token、過期、用過了）**回同一句話**。分開講只幫得上在猜的人。
- 讀者是在第一次要求登入時建立的，不是第一次付款。付款給他的是**客戶**身分（D-024），閱讀給他的是**讀者**身分。

- 文章多一個欄位 `access`（`free` / `members`，預設免費，migration 0039）。

### 3D 辦公室當機：`Cannot set properties of undefined (setting '_cacheIndex')`

使用者回報的執行期錯誤，發生在 `AvatarController.setPose` 呼叫 `.play()` 的時候。

**原因**：`dispose()` 呼叫了 `mixer.uncacheRoot(root)`，那會把 mixer 內部對這些動作的記錄清掉；但 controller 自己還留著那些 `AnimationAction` 物件。再播放其中一個時，three.js 內部的 `_takeBackAction` 會讀到陣列外的位置，於是對 `undefined` 設定 `_cacheIndex`。

**為什麼一定會遇到**：React 在開發模式會「執行 effect → 清理 → 再執行」，而 controller 是 `useMemo` 的值，不會跟著重建。所以「被清掉的 mixer 又被拿來用」不是意外，是每次開發都會發生。

**修法**：`dispose()` 不再 `uncacheRoot`，只停掉所有動作並把姿勢狀態歸零，讓同一個 controller 可以再被使用。不會漏記憶體：mixer 是這個 controller 專屬的，物件被回收時一起消失。

先寫一個測試重現（dispose 之後再 setPose），確認它以同樣的錯誤失敗，再修到它通過。

### 切到 2D 再切回 3D 會顯示「3D 暫停」

使用者回報的第二個問題。**原因**：切到 2D 時，3D 的畫布被銷毀，瀏覽器只能用一種方式說這件事——`webglcontextlost`。元件把它記成「繪圖資源被收回」，而那個狀態在切回 3D 時還留著，於是一個剛建好的畫布被蓋上「3D 暫停」的訊息。

**第一次修法（不夠）**：不在 3D 模式時就把這個狀態清掉。單元測試通過、CI 通過，**但使用者回報照樣出現**。

**為什麼不夠**：事件是非同步送達的。監聽器掛在 `onCreated` 裡、而且從來沒有移除，所以舊畫布死掉時發出的事件會打回同一個回呼——**而且可能在新畫布已經建好之後才到**。那時模式已經是 3D，前一個修法早就跑完了。開發模式更明顯：React 的 StrictMode 會「掛載 → 卸載 → 再掛載」，所以每次進 3D 都會發生一次。

**真正的修法，兩層**：
1. **根源**：監聽改成從畫布內部掛（`ContextWatch`），有 cleanup，卸載時先移除監聽並標記失效。畫布的監聽器跟著畫布的壽命走。
2. **防守**：每次離開 3D 就把「這一輪」的編號加一；事件回報的是它自己那一輪的編號，對不上就不是在講現在這個畫布。

**測試怎麼寫才算數**：先寫「已經消失的畫布不能回報現在這個畫布」，確認**拿掉修正它會失敗**（我實際退掉修正跑過一次）。另外加的 e2e 來回測試**抓不到**這個 bug——e2e 跑的是正式建置，React 不會重複掛載——所以把它的名字與說明改成它真正保證的事：來回切換之後辦公室還在畫。

## 旁支：英文版的標題是中文（2026-09-23）

使用者看英文版公開站時發現標題是「流明市港區社區微電網啟用 市府：停電時可供電六小時: the numbers」。

**查下去是兩件事，只有一件是 bug**：

1. **那篇是模擬模型寫的**（`MODEL_PROVIDER=fake`）。模擬寫手用樣板拼標題：`{來源標題}: the numbers`，而來源標題是中文，於是中文原封不動進了英文版。真實模型不會這樣寫——但示範資料教錯了事。
2. **真正的缺口**：`write_draft` 檢查「兩種語言都在、引用同一組 claim、引文長度、只引用這則新聞未被駁回的 claim」，**但從來不檢查英文版是不是用英文寫的**。R12（雙語事實漂移）靠共用 claim_ids 守住，語言本身沒有人守。真實模型偷懶照抄時，沒有任何東西擋得下來。

### 檢查畫在哪裡：標題與摘要，不是內文

第一版我連內文一起檢查，結果**把模擬資料整批擋掉**——模擬的中文版內文本來就整段是英文的來源引文（`_in()` 明說「模擬不翻譯」）。這逼我想清楚規則該畫在哪：

- **標題與摘要是寫手自己的話**，任何情況下都該是那個語言。讀者是先看到標題才決定要不要點進去的。
- **內文不是**。一篇報導可以大量引用外語來源；用英文證據寫成的中文報導，英文字比中文字多是正常的。

所以規則只管標題與摘要。**一條永遠成立的規則，勝過一條大部分時候對、其餘時候在冤枉人的規則。**

### 這個檢查誠實地說出它不會什麼

它數的是漢字比例，不是語言辨識。zh-TW 與 en 這兩種語言夠用，但它**認不出把法文當英文賣**——docstring 直接寫明，而不是假裝自己是語言偵測。

門檻也留了餘裕：中文標題只要四分之一是漢字就算數（「Lumen City 微電網啟用：4 MWh 儲能」只有三分之一是漢字，那是正常的中文標題）；英文標題可以帶漢字（人名、地名、引用詞），但不能整句都是。

### 模擬寫手

不再把外語標題貼進另一種語言。來源是中文、要寫英文版時，標題改成 "The numbers behind the story"；反過來則是「來源報導的數據一覽」。跟 `_in()` 同一個原則：**模擬不翻譯，但也不假裝翻譯過**。

### 驗證

- `tests/newsroom/test_language.py` 12 個：哪些語言用漢字、只數字母不數標點與數字、各自語言正常通過、**照抄另一語言的標題被擋**、英文標題裡的中文人名是正常的、中文標題裡的英文品牌名是正常的、中文版整篇英文被擋、以及「內文不在這裡判斷」（讀簽名）。

### 第二階段：美術（2026-09-23）

**全部用幾何畫出來，不下載任何素材。** 三個理由，寫在 `console.ts` 的檔頭：

1. 這個檢視同時是「沒有 WebGL」與「手機」的退路，必須夠輕；

3. D-008 規定素材只能用 CC0——**什麼都不下載，這個問題就不存在**。

像素感來自像素畫本來就有的東西：小色盤、硬邊、整數步進、由矩形組成的形狀（`shape-rendering: crispEdges`、`image-rendering: pixelated`）。

| 元件 | 怎麼畫 |
|---|---|
| 地板 | 兩色交替的方格；中央一條走道（3D 樓層也有） |

| 人 | 三個矩形：肩膀（職務色）、頭、頭髮（職務色）。選取時外框一圈 |
| 空位 | 只畫椅子的輪廓——房間有幾張桌子是房間的事實 |
| 盆栽 | 兩個角落各一盆 |

**主控台配色自成一套**，不沿用 3D 的五種風格（D-011）：3D 辦公室是一個房間，你會想佈置它；2D 是一塊儀表板，儀表板只有一種樣子。配色以 CSS 變數掛在 2D 的根元素上，頁面其他地方不受影響。

**差點弄錯的一件事**：代理徽章的色調鍵（`muted`／`active`／`warn`…）跟事件紀錄的色調鍵（`neutral`／`think`／`ok`…）不是同一組。我一開始共用一張表，結果所有徽章都會退成同一個顏色——狀態就看不出來了。分成兩張表 `BADGE_INK` 與 `TONE_INK`。

### 整頁的終端機模式（使用者決定）

做法不是逐個元件改樣式，而是**在頁面根元素上覆蓋應用自己的主題變數**（D-007 的語意 token：`--color-canvas`、`--color-surface`、`--color-line`…）。裡面的元件本來就用這些 token，所以一行都不用改就跟著變；離開 2D 就拿掉，其他頁面完全不受影響。

一個必要的小改動：頁面原本不知道最後是 2D 還是 3D（`auto` 是在畫布裡問瀏覽器才決定的），所以 `OfficeCanvas` 多一個回報：它定案之後告訴頁面。分層規則要求 features 只能透過 `OfficeCanvas` 這道門用辦公室，所以配色函式也是從那裡再輸出的——ESLint 又擋了一次，又擋對了。
### 整層樓與房間輪廓（2026-09-23）

## 2D 第四階段：真的像素精靈，不是矩形（2026-09-23）

使用者給了一張真正的像素風模擬經營遊戲畫面當目標，並指出目前的問題：**看起來像「用矩形畫出來的 UI 示意圖」，不是「2D 像素遊戲場景」**。指示很明確：重構渲染架構，不要在既有圖形上加裝飾，也不要另起一套平行的 renderer。

### 問題出在哪

前一階段每個物件都是「大矩形 + 幾個小矩形」。桌子是一個方塊加兩個小方塊，人是三條橫槓。**沒有輪廓，沒有階調，沒有陰影**——所以怎麼調色都還是示意圖。

### 做法：先有精靈系統，再畫場景

新增 `art/sprites.ts`：精靈用**字元列**定義，一個字元一個像素，對應一張色盤——這就是像素畫實際的作法。

```
"....eeeeeeee...."   螢幕外框
"...essssssse...."   螢幕
"cccccccccccccccc"   桌面
"bbbbbbbbbbbbbbbb"   桌緣（暗一階）
"aa..........aa.."   桌腳
"yy..........yy.."   落地陰影
```

`.` 是透明，所以**形狀就是形狀，不是外接矩形**。繪製時同一列相同顏色合併成一次填色，一個 16×16 的精靈只要幾次 fill，不是 256 次。

`art/atlas.ts` 是這間辦公室的素材庫：色盤分材質（木頭、金屬、綠植、布料、膚色、螢幕、紙、陰影），每種四到五個階調。物件二十餘個：辦公桌（含螢幕、鍵盤、馬克杯）、辦公椅（椅背、椅面、五爪腳）、沙發、兩種盆栽、書架、矮櫃、櫃台、咖啡機、冰箱、爐具、白板、立燈、窗戶、門、地毯、紙張、杯子、餐盤、紙箱，以及**人物**（頭髮、臉、眼睛、手臂、衣服、腿、落地陰影，走路兩幀）。

人物的衣服與頭髮是**繪製時換色**的：同一個精靈，每個代理穿自己職務的顏色。

### 視角與深度

- **牆有頂面與立面**：牆在碰到地板的那一格才畫立面，這是房間高度的來源。
- **地板是磚塊精靈**，三種變體（接縫、細碎斑點），寬闊的地面不會看出重複。
- **由遠至近排序**：每個物件有「腳」的位置，畫面依此排序，所以站在桌前的人會遮住桌子，站在桌後的不會。
- 地毯的腳設為 `-1`：它是地面的一部分，永遠在最底層。

### 密度

每個房間有它該有的東西，位置從房間自己的方框算出來：接待區有櫃台（上面有咖啡機、餐盤、杯子）、沙發、地毯、立燈、盆栽、矮櫃；茶水間有冰箱、爐具、一整排流理臺與杯盤；會議室有白板、長桌與兩側的椅子、地毯；執行長室有書架、矮櫃、地毯、立燈、盆栽。開放區每個角落有盆栽、矮櫃、紙箱，走道兩側每隔幾公尺有盆栽和紙箱，上方牆面每隔五格有一扇窗。

### 驗證

- `board2d.test.tsx` 23 個全過（場景模型的測試不需要畫布）。
- web 335 個測試通過、`lint-web` 通過。
- 真實瀏覽器截圖比對。
- 互動、走動、房間分頁、點選、縮放都照舊——這次只換了「畫什麼」，沒有換「怎麼互動」。

### 一件小事

完整測試跑了一次時間軸的測試失敗，單獨重跑通過、再跑一次完整也通過——那是個不穩定的測試，跟這次的改動無關。記在這裡，之後若再出現就去修它。

## T-702：統一金流（PAYUNi）一次收款

D-024 決定的收款方式，這一批把它做完並且實測跑通了一次完整流程。

### 信封

統一金流每一則訊息——送出的請求、回傳的通知——都是同一個形狀：欄位排成查詢字串、加密，再附一個雜湊讓雙方確認沒被改過。

    EncryptInfo = hex( base64(AES-256-GCM 密文) + ":::" + base64(tag) )
    HashInfo    = SHA256( HashKey + EncryptInfo + HashIV ).upper()

**這裡「差不多對」等於「錯」**：解不開的通知是一筆收不到的錢；把不是統一金流送的訊息當成真的，是白送一年會員。所以測試不只拿自己的兩個方向互相驗證（兩邊錯得一樣就會一起通過），而是另外用 Node 照官方 PHP SDK 的步驟獨立實作一次，產出一組向量存成 `payuni_vector.json`，再驗證我們的 Python **解得開別人封的信封**、而且**封出來的位元組完全一樣**。

### 訂單

付款通知裡只有金流商說的話，所以要有一張我們自己先寫下來的東西可以對。流程是：開訂單（PENDING，帶我們自己的 `MerTradeNo`）→ 讀者在統一金流的頁面付款 → 統一金流伺服器對伺服器送通知 → 通知通過四道檢查才變成一年。

四道檢查，以及各自在擋什麼：

- **信封**（`infra/payments`）——沒有人封過的通知不是通知；
- **交易編號是我們開過的**，而且是這個金流商的；
- **金額是當初開的那個金額**——說不一樣的，不是出錯就是有人在試；
- **金流商說付款成功**（外層 `Status=SUCCESS` 且 `TradeStatus=1`）。

四道都過，付款、帳本、會員資格在同一個交易裡一起寫。重送不會有第二筆（冪等鍵是金流商自己的交易編號）；已經 PAID 的訂單再收到通知，回的是它第一次買到的東西。

**拒絕的回覆刻意沒有內容**：金額不符和查無此單回的是同一句話，因為會讀到那句話的只有在猜交易編號的人。

### 沒有連到統一金流

沙箱商店還沒申請到能實際下單的狀態，所以**這一批沒有碰過統一金流的伺服器**。能證明的是：加解密與官方演算法一致（獨立實作交叉驗證）、四道檢查每一道都擋得住、整條流程在本機真的跑通。不能證明的是統一金流同不同意我們對它文件的解讀——那要等沙箱。

## 2D 烘焙（D-026、D-027）：第一步，管線

使用者傳來一張**手動把 3D 相機轉到接近俯視**截的圖，意思是「3D 已經是好看的 2D 圖了」，並說角度抓得不準、請我修正。另外兩個要求：2D 要跟著 3D 的風格切換一起變；以及問了一句「需要切換模型來畫圖嗎」——不用，這裡沒有任何影像生成，精靈圖是用專案自己的 three.js 幾何算出來的。

### 為什麼烘「材質槽＋明暗階」而不是烘顏色

烘顏色的話，五種風格要五份圖，之後每加一種風格就要再烘一次。改成每件家具烘三遍：

1. **不打光、每個調色盤槽塗成專屬的探針色**——讀回來的顏色就是「這個像素是桌面、是椅子、是葉子」；
2. **只打光、全白**——讀回來的亮度就是形體：桌面亮、正面中、右側暗，量化成 5 階；
3. **沿主光把幾何壓扁到地面**——投影。

一個字元代表一組（材質槽, 明暗階）。執行期拿當前主題的調色盤查表，換風格就是換一張表。**這個格式剛好就是現有 `Sprite` 的形狀**（字元列＋調色盤），所以 `drawSprite`、翻轉、依腳底排序全部不用改。

### 過程中踩到的

- **Playwright 的 Chromium 下載逾時**。改成找不到就用這台機器的 Chrome；另外明確要求 SwiftShader——無頭 Chrome 沒有 GPU，靜悄悄烘出一張空圖比直接失敗更糟。
- **從畫布 `readPixels` 讀到全透明**。改成渲染到 render target 再讀；顏色比對放在線性空間做，不去還原 renderer 的色彩轉換。
- **以為相機角度沒套上**，實際是 bounding box 的空角落被裁掉，加上 16 px/m 的椅子本來就只有 10×8。做成參數、烘三個角度比對之後才確定相機沒問題。
- **椅背的條紋是透明的**：條紋是角色色，不在調色盤裡。改成一個可替換的 `accent` 槽——2D 本來就要把椅子染成坐的人的角色色。
- **`approvalDesk()` 蓋在它在辦公室裡的位置，不是原點**，錨點偏了 92 像素。是新測試「每件家具站在自己的圖裡」抓到的。

### 從「低解析度截圖」到像素畫

第一版對照表認得出每件家具，但看起來是縮小的 3D 截圖。補了三樣：

- **外框**（sel-out）：外框取相鄰材質最暗的一階。第一版冷色偏移太重，全部變成深藍框，調小之後木頭是深棕框、葉子是深綠框。
- **投影**：跟明暗用同一個主光方向，所以影子形狀和 3D 一樣。第一版光太低，棕櫚的影子比棕櫚大一倍，抬高光源後收在家具底下。
- **電光風的霓虹邊**：深色家具在深色地板上等於不見了。有 `glow` 色的主題，外框改用建築的霓虹邊色——3D 的電光風本來就是靠發光的邊線認東西。

## 一顆我自己埋的時間炸彈：讀者登入的測試在 09:15 UTC 引爆

烘焙管線的檢查點（`9866955`）CI 失敗在 **python**——那一批完全沒動 Python。7 個失敗全在 `tests/accounts/test_login.py`，錯誤是 `login_tokens` 違反 `expires_at > created_at`。

**原因**：今天早上寫讀者登入（D-025）時，測試把時間固定在 `2026-09-23 09:00 UTC`，所以連結在 09:15 到期。但 `created_at` 是**資料庫用自己的時鐘**蓋的。CI 在 09:24 跑，created_at（09:24）晚於 expires_at（09:15），約束就擋下來。今天稍早的 CI 會過，只是因為剛好在 09:15 之前跑完。

**不只是測試的問題**：服務拿呼叫者的時鐘算到期時間，拿資料庫的時鐘算建立時間，然後讓資料表比較這兩個時鐘。正式環境兩者通常一致，但這個設計本身就在賭兩台機器的時鐘差不到 15 分鐘。

**修法**：服務寫入時 `created_at` 跟 `expires_at` 用同一個 `now`（登入連結與工作階段都是）。另加一個測試：用 2020 年的時間要一條連結，它必須跟自己一致——這個測試跟 CI 在幾點跑無關，拿掉修正會失敗（驗證過）。也搜過其他資料表：比較 `created_at` 的約束只有這兩個。


## 2D 烘焙第二步：2D 看板改成畫 3D 的辦公室本身

接線時發現一件事：2D 的**座位**本來就跟 3D 同一份配置，但**裝飾**（盆栽、書架、冰箱、沙發、白板⋯）是 `tiles.ts` 另外手擺的，位置跟 3D 不一樣。這是 2D 一直不像使用者那張 3D 俯視截圖的另一半原因——不只是畫得不好，是擺得不一樣。

### 2D 不再擺家具

`scene/furniture.ts` 新增 `placedPieces()`：從 3D 自己用的座位、長桌、`DECOR` 清單、審批櫃台列出「每件東西站在哪」。烘焙時把這份清單連同精靈圖一起寫進 `baked.ts`，2D 照著畫。3D 移一盆植物、重烘一次，兩邊一起動。

- **房間的殼**分兩種：永遠在後面的（地板、後牆與左牆、窗、投影幕、前緣）烘成**一張背景**先畫；會擋住別的東西的（後排房間的玻璃隔間、房間之間的牆）烘成**零件**，跟家具一起依腳底排前後——否則會議室的椅子會畫到它前面的玻璃牆上。
- **玻璃隔間只烘框、不烘玻璃**：不透明的玻璃會擋掉後排房間前面 1.5 公尺，使用者的截圖裡玻璃是透的。
- **只有某些風格才有的零件**（電光風的區域霓虹邊線、桌緣發光）一律烘進去，風格沒有那個顏色時退回它底下的顏色：邊線退成那一區的地板色、桌緣退成桌面色。一次烘焙涵蓋五種風格。

- 拆 `architecture()` 和 decor 建構函式時，**3D 辦公室一個零件都沒變**：五種風格的零件數與矩陣總和，改之前改之後逐一比對相同。

## 人物烘焙（D-028）

2D 的每個人現在都是他在 3D 裡的那個角色，坐、走、站都照 3D 的方式擺。

### 做法

- 12 個 Kenney 角色，照 3D 同一組數字擺姿勢：放大 2 倍、頭縮 0.8、坐著抬高 0.41 公尺、用同樣的動作片段（`sit`、`walk`、`idle`）。為了讓烘焙不用載入 React，這幾個數字從 `AgentAvatar.tsx` 移到 `agents/body.ts`，3D 和烘焙讀同一份。
- 每個角色 16 張：坐著（背影）、走路三個方向各 4 格、站立三個方向；左側面是右側面的鏡像。共 192 張。
- 角色的 GLB 用相對網址載入旁邊的貼圖，`file://` 頁面不准這樣讀，所以烘焙工具改成用 Playwright 攔截一個假網域 `http://bake.local`，所有請求都從本機硬碟回應，不連外。
- **顏色取自角色貼圖**，不跟風格換（3D 也是這樣）。貼圖有 255 色，一個角色乘上 5 階明暗會超過鍵的字元上限，所以每個角色減到 10 色：中位切割，每組取最常見的**真實**貼圖色，而且對同一角色的所有姿勢一起算，走路時顏色不會跳。

### 兩個看起來像 bug、其實不是的地方

- **手臂都水平張開**：我先以為動畫沒套上（骨架預設的 T 字姿勢）。實際讀了骨頭的旋轉：預設是 `[0,0,0,1]`，`sit` 轉 45°、`idle` 轉 30°，動畫有套上。Kenney 的 Q 版角色手本來就往外張，從 61° 往下看就像水平。
- **female-a 手上長長的藍色**：懷疑是 10 色減色把顏色併錯。用她自己的 3D 材質另外渲染一張參考圖比對：她的袖口本來就是藍色。

### 接進 2D

- 坐著的人畫在椅背後面、面向螢幕；完成的人站在椅子後面（3D 的 `STAND_BACK`）；走路的人依方向換圖、每 167 毫秒換一格（3D 的走路片段 0.67 秒四格）。

## 地板紋理（D-029）

2D 地板原本是純色。現在每一區照 3D 的材質鋪：木地板、磁磚、石板、地毯方塊、電光風的發光網格。

### 為什麼不烘進圖裡

同一塊地板在不同風格是不同材質：開放區在日式無印是木地板、工業風是水泥板、電光風是網格；大小也不同（1.2、1.6、1 公尺）。烘焙是所有風格共用一次，裝不下，所以紋理在「用某個風格上色背景」時才鋪，每種風格只做一次。

只有地板像素會被改：烘焙記得每個像素是哪個槽，牆、窗、前緣、外框都不碰。每個地板像素知道自己在辦公室的位置（一公尺橫 32、縱 28 像素），所以接縫落在跟 3D 一樣的地方。

### 調整

第一版木地板看起來像磚牆：一排木板只有 8 像素深，照 3D 的接縫深淺（64 像素裡 2 像素）畫在 1/8 的比例上太重。把接縫調淡之後才像木板。

### 一個我弄壞、只在本機的東西

### 測試

木地板每 1.2 公尺四排接縫、磁磚每 0.25 公尺有 3D 的灰縫、網格每公尺一條且中線較淡、沒有紋理的地板不動、同一塊地每次都一樣、五種風格的每一種有紋理的地板都真的畫出東西、只改地板不碰牆和外框。


### 終端機模式那個 e2e：第二次失敗，而且時間點指向我

地板紋理（`ebebb92`）第一次 CI 又是同一個測試、同一行失敗，同一提交重跑通過。把紀錄排起來：人物那批（`5d6cfc4`）之前約 9 次全過；之後 4 次失敗 2 次。所以不能再說「跟這批無關」。

我先前的推論是：2D 看板是延後載入的，但不在「按 2D → 終端機模式」這條路上。查了 Next 的 `dynamic()`：`ssr: false` 時它會自己包一層 Suspense，理論上切換會先顯示「載入中」並立即完成，推論本身沒錯。但實際上這兩批也讓切到 2D 的第一幀變重（解碼人物與背景、畫背景、這批再加上鋪地板紋理），在慢的 CI 機器上可能擋住那次重新繪製。

正在修這個測試的另一個工作階段已經收到這些證據；如果是產品本身變慢，修法應該在產品裡（例如把第一幀的重工作移開、或在辦公室頁閒置時預先載入 2D），不只是改測試。

### 終端機模式的 e2e：量出來是 3D 起步卡住，測試改成等場景穩定再切換

**先說結論：頁面沒有壞，切換本身不慢；改的是測試。** 測試在 3D 剛起步、還在畫第一批畫面時就按 2D，而 CI 的軟體 WebGL（SwiftShader）這幾幀會卡住主執行緒約 5 秒。

**兩次失敗的 trace（`35847067161`、`35856488949`）長得一樣**：按下 2D 之後 0.1 秒，3D 才開始抓角色的 GLB；再 0.9 秒，2D 看板的程式碼區塊送達；接著畫面錄影停了 **5.6 秒**（兩次都是 5.6 秒），GLB 的貼圖要等到之後才去抓。斷言 5 秒逾時，剛好落在卡住的期間。

**本機重現**（Chrome + SwiftShader，用 Long Animation Frames 看每一段長畫格是哪支程式）：

| 情境 | 按下 → `data-terminal="true"` | 按下之後最長的一格 |
|---|---|---|
| 一開 3D 就按 2D（舊測試的做法），CPU 放慢 4 倍 | 9.6–10.7 秒 | 4.6–5.4 秒，R3F 的畫格回呼（3D 區塊），大部分時間不在 JS 裡：在等 GPU 行程 |
| 只開 3D、不按 | — | 5.3 秒，同一個畫格回呼：**不按也會卡** |
| 等場景穩定再按 2D（新測試），CPU 放慢 4 倍 | 0.42–0.43 秒 | 約 0.9 秒（R3F 收掉畫布的計時器） |
| 從 2D 切回 3D，CPU 放慢 4 倍，三次 | 0.20–0.23 秒 | 新畫布第一格 1.8–2.1 秒，在 `data-terminal` 變回來**之後** |

整個瀏覽器（連 GPU 行程）放到 macOS 的背景優先權、像一台慢機器時，**原本的測試 6 次失敗 1 次**（第一次、著色器快取還是冷的，同樣是第 185 行、`Received: "false"`）；**新測試同條件 6 次全過**，包含第一次。正常本機 Chrome：兩個切換測試各 5 次全過；`office.spec.ts` 12 個全過。

**為什麼從 `5d6cfc4` 開始才出現**：那一批把 2D 看板改成延後載入。量到的順序是「看板區塊先執行完、2D 才提交」，查了 React 19.3 的 work loop：轉場（transition）中的渲染碰到還沒好的延後載入元件時，React 會**暫停渲染等它**，不是立刻顯示「載入中」。等的這段時間 3D 畫布還掛著，它最重的那一格就會插進來。改成延後載入之前，同樣一開就按，本機量到 4.55 秒切完，畫布在重畫格之前就被拆掉了。所以失敗的時間點確實跟那一批有關，但卡住的是 3D 起步，不是看板。

**跟看板有關、但不是這次原因的一件事**：`ebebb92` 的地板紋理讓看板第一次繪製從 73–79 毫秒變成 611–750 毫秒（CPU 放慢 4 倍時）。它發生在 `data-terminal` 變成 true **之後**，所以不影響這個測試；但對慢機器上的使用者是真的慢了約 10 倍，值得另外看。

**改了什麼**：`e2e/office.spec.ts` 加了 `sceneSettled()`：先等 3D 畫布出現，再等畫格探針（`window.__autoraOffice`，每秒回報一次）連續兩次回報的繪製次數和三角形數一樣，也就是角色都進場、畫了至少一整秒同一個場景。「終端機模式」和「切到 2D 再回 3D」兩個測試都在按 2D 之前等它。每個測試多約 2 秒。**產品程式碼沒改**，逾時也沒調。

**沒做、留給產品決定的**：如果要讓「3D 還在起步時按 2D」也立刻切，修法在產品裡。例如辦公室頁閒置時先載入 2D 看板的區塊，轉場就不用等它。真機有 GPU 時，第一格只要幾百毫秒；而 Chrome 預設不讓一般使用者用軟體 WebGL，沒有 GPU 的人本來就會拿到 2D。所以實際影響只在「有 WebGL 2、但很慢」的機器上，起步那幾秒按 2D 會延遲。


## 地板紋理讓 2D 第一幀慢了十倍：修掉

另一個工作階段（修終端機模式 e2e 的那個）量測後回報兩件事：

1. **那個 e2e 的主因是 3D 場景的第一幀**（GPU 行程上約 5 秒，沒點任何東西也會發生），他們已在測試裡改成等 3D 穩定後才切換（`7b91303`）。**我先前的推論有一處是錯的**：我說 Next 的 `dynamic()` 自帶 Suspense，所以切換會先顯示「載入中」並立即完成。實際上在這個 React 版本，導航（transition）遇到還在載入的延後元件會**等它**，而不是先顯示 fallback——於是 3D 畫布多留了一陣子，它的重第一幀剛好落在切換裡。延後載入確實把那個窗口撐大了。
2. **`ebebb92` 的地板紋理讓 2D 第一幀慢了約十倍**。這是我造成的，這批修掉。

### 原因與修法

量測（無頭 Chrome、CPU 放慢 4 倍、整個第一幀：場景加上每張圖從空快取畫起，中位數）：

| 版本 | 日式無印 | 電光風 |
|---|---|---|
| `6246675`（紋理之前） | 39 ms | 38 ms |
| `ebebb92`（加上紋理） | 682 ms | 535 ms |
| 這批 | 73 ms | 79 ms |

慢在兩處。**主要**是鋪紋理的方式：先把背景用幾千個矩形畫到畫布上，再 `getImageData` 讀回來鋪紋理、`putImageData` 寫回去——讀回畫布要等 GPU，810×522 的背景在慢機器上要幾百毫秒。**次要**是紋理迴圈每個像素建三個小物件。

改成：每張圖直接在陣列裡算出每個像素（顏色本來就知道），紋理鋪在陣列上，最後一次 `putImageData`，不再讀回畫布；紋理迴圈改用預先算好的欄列座標、依字元碼查地板。**輸出完全相同**：五種風格的紋理輸出指紋逐一相同，整層樓的預覽圖與 D-029 的圖**逐像素比對 0 個差異**。

比紋理之前仍多約 35 毫秒（放慢 4 倍；一般機器約 9 毫秒），這是鋪紋理本身的成本。試過「只有背景用陣列、小圖仍用矩形」反而更慢，所以維持全部用陣列。

量測工具留在 `tools/bake-sprites/time.mjs`，之後動到 2D 繪製可以重跑。

### 過程中的一個失誤

做版本對照時，我寫的 shell 指令在 zsh 下出錯：變數沒被拆開，所以備份沒做成；`$rev:fr…` 被 zsh 當成修飾符，`git show` 失敗，但 `>` 已經先把三個**尚未提交**的檔案清空。已提交的東西不受影響。我照這個工作階段裡的修改原文逐一補回，並用同一組輸出指紋確認補回的結果與原本**逐位元組相同**。之後的對照改用 `/bin/bash` 並先確認備份。


## 背景預先載入 2D（D-030）

使用者決定：要。3D 辦公室的畫面空閒下來後，就在背景把 2D 看板下載好，之後在 3D 啟動中切到 2D 不用再等它下載。

## T-707：營收儀表板

使用者：「先做 T-707 營收儀表板」。儀表板原本只有「今日營收」一個數字；付款、帳本、會員資格都有資料了，但沒有地方看得到。

### 算什麼、從哪算

新的核心模組 `company/revenue.py`，每期報表（CEO 透過公司快照讀）和儀表板都從這裡拿，所以兩邊不會對不上。

| 數字 | 定義 |
|---|---|
| 付款 | 這段期間的付款筆數 |
| 新會員 | 客戶的**第一筆**付款；看單一事業時是「在這個事業的第一筆」 |

## T-705：財務代理（D-031）

使用者：「做 T-705 財務代理」。驗收只有一句：**沒有任何寫 transactions 的路徑**。

### 它做什麼

每一期量測完（MEASURING），報表把營收、成本、會員數寫進 KPI 之後，財務代理讀同一份公司快照和今天設定的預算，判斷哪個預算已經不符合現況——例如某個事業沒有收入卻有很大的預算、成本漲得比營收快。它最多提三個調整；什麼都不提時要說理由（「數字都正常」是結論，沉默不是）。

提案就是一道 `AllocateBudget` 指令。財務角色送出這道指令，政策**一律**開審批給人；人核准了，才照原本的流程寫進 `budgets`。到了下一個階段（REVIEWING），提案已經在審批收件匣裡等人決定；CEO 的快照只看得到待審的**數量**，看不到提案內容。

### 為什麼它碰不到帳本

| 可能的路 | 怎麼擋 |
|---|---|
| 直接呼叫別的工具 | 它只有一個工具：`submit_command` |
| 透過指令做別的事 | 政策對財務角色只允許這一個工具本身；其他動作全部沒有「允許」。`record_transaction` 沒有規則，所以拒絕；`payment` 是不可逆動作，引擎一律要人 |
| 預算提案被核准 | 核准寫的是 `budgets`（花費上限），不是 `transactions` |
| 有指令能記交易 | 根本沒有：指令匯流排上沒有任何動作是 `record_transaction` |
| 程式碼直接寫帳本 | 財務的兩個模組沒有匯入帳本或交易模型（測試用語法樹檢查） |

另外有**第二道鎖**：驗證器會查這一輪送出的 `AllocateBudget`，任何一筆不是「等待審批」就退回。政策已經有測試保證不會發生；這道鎖是給「哪天有人放寬政策」用的。

### 引用的數字要對得上

每個提案要附依據：指標名稱、範圍（公司／事業／專案）、數值。驗證器逐一去找這一期存下的 KPI 比對，找不到、範圍沒指明、數值不同都退回（數值用 Decimal 比，`412.5` 和 `412.500000` 算相同）。另外檢查：提案回報的審批編號必須是這一輪開的、送出幾道就要回報幾道、提案的事業或專案必須是這家公司的、不能同時指定事業和專案。

### 接線

- `company/finance.py` 的 `FinanceDesk`：MEASURING 進場時，在報表的掛鉤**之後**開一個單節點工作流程（`company.budget_review_v1`），費用記在公司自己的營運專案；同一期只開一次。MEASURING 要等這個任務結束才算完成（或是階段期限到）。
- **沒有聘財務代理的公司照舊**：不開任務，MEASURING 立刻結束。
- 行政部門多一個「CFO」職位（`finance`）。新公司建立時就有；**已經存在的公司不會補上這一列**（沒有寫 migration）——聘財務代理照樣可以，只是組織圖上沒有那張椅子。示範公司每次 seed 都會補上。
- 聘人的 API 現在會把代理放進同名的職位。
- 模擬模式的財務長會讀快照裡上一期的營收與成本，回報「不調整」。
- 前端：`finance` 在辦公室和面板都顯示「財務長」。財務代理屬於行政部門，所以 3D／2D 裡坐在執行長那一區。

## T-706：商業代理（D-032）

使用者：「做 T-706 Business 代理」。

### 先看 T-611 已經涵蓋多少

T-611 之後，商業迴圈已經有 CEO 評估機會、策略師把機會寫成提案、人核准開事業。**缺的是起點**：`opportunities.discover` 和 `add_signal` 兩個函式都在，但正式程式碼裡沒有任何呼叫者，測試裡的機會全是手動塞進去的。資料表甚至早就留了 `discovered_by_run_id` 欄位等代理來填。所以 T-706 做的是「發現機會」的那一步。

規格有兩處互相矛盾，所以問了使用者：
- T-706 寫「→ HUMAN」，但後來的架構 v2.1 §6 說發現機會便宜、可逆，不需要人審。使用者選**照 v2.1**：代理自己記錄，人仍然把關開事業和動用資本。
- 資料來源，使用者選**公司數據 + 網路搜尋**。

### 它能做什麼

只有兩道新指令，都只是「寫下來」：
- `DiscoverOpportunity`：新增一個機會（狀態 DISCOVERED），至少附一個訊號。
- `RecordOpportunitySignal`：替還在考慮中的機會加一筆觀察。

政策對 business 角色只允許：`submit_command`、這兩道指令，以及三個讀網頁的工具（`web_search`、`fetch_url`、`read_evidence`）。打分、推進、否決、寫提案、配預算、開事業一律不允許，測試逐一問過政策知道的每個動作。

### 寫進去的東西要拿得出證據——寫入當下就查

| 訊號來源 | 檢查 |
|---|---|
| `company`（公司自己的數字） | 必須附指標與數值，而且等於最近一期報表存的值（數字比數字，`2` 等於 `2.000000`）；可以指定某個事業的報表 |
| `web`（網頁） | 必須引用**這一輪任務的工具自己抓下來的**東西（`TOOL_COMPLETED` 事件裡的 `produced`）。別輪抓的、沒抓過的、直接貼網址，都拒絕 |
| `person`（人說的） | 代理不能用；人可以，而且人寫的不檢查（紀錄會寫是誰） |

另外：一次觀察最多新增 3 個機會；已經決定過（否決、過期、核准）的機會不能再加訊號，也不能用同一個 key 重新發現——被否決的機會是公司的決策記憶，要它說明「否決的理由已經不成立」才會另立新的。

**先全部檢查、再寫入。** 反向驗證時發現：指令管線在處理器拒絕時**不會**回滾它已經寫下的東西（沒有 savepoint）。所以「一個機會附兩個訊號、第二個是編的」要整筆不寫，靠的是處理器先查完所有訊號才動資料庫；測試拿掉這個順序會失敗。管線本身沒有這個保證這件事，我另外開了一個待辦（稽核所有處理器、加 savepoint），沒有在這次擴大範圍。

### 工具從哪來

網頁搜尋與抓取屬於新聞室領域，Core 不能 import 領域。所以商業代理在 Core 裡只接受「別人借給它的工具」：`app.py`（組裝根，唯一允許把兩邊接起來的地方）的 `RESEARCH_TOOLS` 把新聞室的三個工具借給它，同時在政策加上對應的允許。沒有借工具時，它就只看公司自己的數字，提示詞也會跟著說明。

公司數字的比對原本寫在財務代理裡，這次抽成 `reporting.figure_issue`，財務和商業兩個代理共用同一份。

### 什麼時候看

- 每週一次，在 EXECUTING 進場時。條件：有在職的 business 代理，而且 7 天內沒有未失敗的觀察。比較時容許 12 小時誤差，否則這週的 cycle 只要比上週早幾分鐘開始，就會拖到隔天。
- 失敗的觀察不算數，停機不會讓公司少看一週。
- EXECUTING 本來就會等當期所有工作流程結束，所以觀察是當天工作的一部分。CEO 在 REVIEWING 會在快照的「待評估機會」裡看到新發現的（DISCOVERED 屬於開放狀態）。
- 費用記在公司的「Market watch」專案上，kill criteria 和探索一樣（成本超過上限就暫停）。被暫停後要有人恢復才會再看。
- 沒有聘商業代理的公司照舊，不會開任何任務。

### 其他

- 行政部門多一個「Business Development」職位；前端顯示「商業開發」。新公司建立時就有這張椅子；**既有公司不會補上**（沒寫 migration），示範公司每次 seed 會補。**目前沒有任何公司聘了商業代理**——要啟用，得在這個職位聘一個代理。
- 模擬模式的商業開發只回報「目前有幾個開放中的機會」，不發現任何東西：編出來的機會會讓 CEO 花一次真的評估。

### 驗證

- 權限矩陣**刻意**加了一欄 business、兩列新動作（多 63 個參數化測試）——這是這個任務本身的改變，不是修壞了什麼。組織圖 API 的測試同樣刻意改成三張椅子（依 key 排序：business、ceo、finance）。

## T-708：階段 7 驗收（D-033）

使用者：「做 T-708 階段 7 驗收」。驗收條件（`13` §2）有兩條：一筆真實 revenue 由 webhook 寫入，並出現在 Dashboard 與 CycleReview；Marketing 超額被攔。

### 怎麼驗

`tests/acceptance/test_revenue.py`，照階段 6 驗收的做法：真的 worker、模擬模型、只有時鐘是假的。

1. 建一家公司：CEO、財務長，年費 NT$360 開賣。
2. 當天這一期開始（測試自己開，時間設在一分鐘前，讓付款落在這一期裡）。
3. 讀者用 Email 登入、結帳；統一金流的付款通知用商店金鑰**照統一金流的方式加密**，送到真正的 `/api/payments/payuni/notify`。
4. worker 跑完一整天：帳本結算、報表量測、財務長讀帳、CEO 覆盤。
5. 檢查帳本、儀表板、操作者看的那一期，以及財務長和 CEO 實際拿到的文件（把模擬模型收到的請求記下來，不改它的回答）。

### 結果

| 條件 | 結果 | 說明 |
|---|---|---|
| 付款由 webhook 寫入 | ✅ | 一筆付款、帳本一筆 NT$360 營收，來源是整合 |
| 出現在 Dashboard | ✅ | `/kpis` 的營收區塊：總額 360、1 筆付款、1 位新會員、會員 1 位 |
| 出現在那一期（操作者看的 CycleReview） | ✅ | `/api/cycles/{id}`：有 CEO 的 review，量測到營收 360、新會員 1 |
| 出現在 CEO 覆盤時拿到的文件 | ❌ → ✅ | **原本沒有**，見下節；修正後 `last_cycle` 就是這一期，KPI 有 360 |
| 出現在財務長讀帳時拿到的文件 | ❌ → ✅ | 同上 |
| 「真實」：真的經過統一金流 | ⚠️ 沒驗 | 沒有連統一金流的伺服器：沙箱商店還不能下單。驗到的是我們這一側的全部檢查 |
| Marketing 超額被攔 | ✅（但書） | T-703 延後（D-022：沒有付費廣告），所以驗的是：行銷代理只有 `create_distribution`、`read_draft` 兩個工具，也沒有任何能花錢的工具；等著的 `spend_ad_budget` 規則在上限內允許、超過或不知道上限都送給人 |

### 驗收抓到的問題：代理覆盤時看不到當天的數字（D-033）

快照的 `last_cycle` 原本是「最近一個**已結束**的 cycle」，而且只有在「最新一筆公司 KPI 屬於那一期」時才附上數字。但財務長在 MEASURING、CEO 在 REVIEWING 的時候，當天這一期還沒結束，最新一筆 KPI 卻已經是今天的——兩個條件互相排除，所以**公司層級的 KPI 一律是空的**，第一天連期數都沒有。代理只能從 `portfolio` 各事業的數字看到營收。

這影響前面兩個任務的說法：
- T-707 寫「每期報表同樣的數字給 CEO」——CEO 確實拿到了，但要到**隔天 PLANNING** 才看得到公司層級的數字，覆盤當下是空的。
- T-705 的財務長被要求「照快照給的數值引用」，但讀帳當下快照的公司層級數字是空的，只有各事業的數字能引用。

**改法**：最新一筆公司 KPI 屬於還沒結束的那一期時，`last_cycle` 就描述那一期。隔天 PLANNING 時結果和以前一樣，所以 PLANNING 與備援計畫的行為不變。新的單元測試和驗收測試，拿掉修正都會失敗（驗證過）。

### 另一個順帶修掉的東西

驗收測試是第一個「真的提交」讀者資料的測試。登入的測試原本查整張表（例如「session 表裡唯一的一列」），又都用同一個 Email，所以驗收測試先跑，登入測試就會失敗。改成每個登入測試用自己的讀者、查詢限定在自己的讀者；驗收測試也用自己的 Email。這是測試彼此依賴的問題，程式本身沒有壞。

### 驗證

- 驗收 2 個測試、快照新增 1 個。
- 後端全部 1633 個測試、lint、匯入規則；前端 lint、型別檢查、547 個測試，全過。

### 階段 7 還剩什麼

- **統一金流沙箱實測**：一筆真的經過統一金流的付款。等沙箱商店能下單，而且要你同意才會連線。
- T-703（廣告上限）與 T-704（外部通路）照 D-022 延後。

## D-034：月繳與年繳、會員方案頁與三份政策

### 順帶發現：付款完回來是 404

`PAYUNI_RETURN_URL` 指向 `/news/zh-TW/membership/done`，但這個頁面從來沒有做。統一金流用表單 POST 把讀者帶回來，頁面收不了 POST，所以：

- `membership/return` 是路由，POST 和 GET 都回 303 轉到 `membership/done`，不讀統一金流帶回來的任何東西（會員資格只由伺服器之間的通知給）。
- `membership/done` 每 2 秒問一次 API「是不是會員了」，最多 10 次；是就寫到期日，沒登入請他登入，一直沒等到就說「還沒收到付款確認」並給聯絡信箱。
- `PAYUNI_RETURN_URL` 的預設值與 `.env.example` 改成 `/membership/return`。
- 「狀態不能由計時器推動」的檢查（AC-S6）原本禁止 `features/` 裡出現任何計時器；done 頁的計時器只是等一下再問 API，在測試裡**點名**允許這一個，跟 socket 的三個計時器同樣處理。
