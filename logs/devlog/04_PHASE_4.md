### 做了什麼
- `/office` 現在是：標頭（顯示方式切換、Dashboard 連結、連線狀態）+ **迷你 Dashboard 列**（現金、今日營收 / 支出、工作中代理、進行中任務、待審批；與 Dashboard 共用 `dashboardModel`，兩頁數字一定一致）+ 辦公室（3D 或 2D 看板）+ **代理詳細面板**（與 Dashboard 同一個，T-310）。點人物（3D）或卡片（2D）→ 選取 → 面板打開；`Esc` / ✕ 關閉。
- 面板蓋住右側 448 px：選取時相機把人物放在**沒被遮住的區域中央**（`OfficeCanvas` 的 `selectionInsetRight`，3D 層只知道「右側要留多少」，不知道面板；窄螢幕面板全寬時不偏移）。截圖時發現選右邊的人會被面板擋住而加上。
- 測試用探針 `window.__autoraOfficeCues`（目前誰在走路、累計走了幾趟），供瀏覽器測試與 T-412 長時間測試使用。

### 驗證（階段 4 驗收的瀏覽器部分）
- `e2e/office.spec.ts` 新增 3 個：
  - **點人物 → 300 毫秒內面板顯示即時狀態**：在頁面內量「按下滑鼠 → 面板出現在 DOM」，實測 **4～7 毫秒**；面板標題是點到的人、即時分頁的狀態與頭頂標籤一致；`Esc` 關閉。
  - **一次執行**：在頁面內記錄每個頭頂標籤的變化——三人都先忙（思考 / 工作 / 檢查）才完成，且依序研究員 → 分析師 → 寫手完成；交接走路至少兩趟（研究員→分析師、分析師→寫手）；迷你列跟著變。

## 使用者回饋（2026-09-19，待辦 → T-413）

看過目前的 3D 辦公室後，使用者提出（並說可以之後再改）：
1. **配色**：整體顏色搭配的協調感不夠，不像專業的辦公室室內設計。
2. **空間區分**：目前有執行長室、會議室、茶水間、各部門、休息（相談）區——辦公室空間是怎麼區分的？依部門切換嗎？
3. **大門口 / 玄關在哪？**
4. 人物的大頭好像過大。
5. 之後可以考慮讓使用者做一點外觀微調，或提供幾套風格切換；太複雜就先不要。

目前的狀況與方向（記錄，T-413 處理）：
- 空間**依角色（部門）分區、同一層樓**，不是切換頁面：研究區（研究員、分析師）與編輯區（寫手、編輯）是兩張長條桌；前排是行銷與給新角色的空桌；後排是執行長室、會議室、茶水間；右前方是審批櫃台與休息區。區隔目前只靠地板顏色與走道，缺少明確的邊界與標示。
- **目前沒有大門與玄關**：前緣是剖面。可以在前方開一個入口，把審批櫃台改成接待 / 玄關。
- 頭部比例：Kenney 素材本身是大頭 Q 版；可以在程式裡縮小頭部骨頭（不改素材檔）。
- 風格切換：顏色集中在 `palette.ts` 並用頂點色合併，切換「幾套調色盤」可行（切換時重建一次網格）；給使用者細調個別顏色比較複雜，先不做。

## T-408 · Courier（交接走路）

### 做了什麼
- **人物本身就是信差**（不另做分身）：`AgentAvatar` 每幀查自己有沒有進行中的走路提示；有的話依 `courierState` 決定位置、朝向與姿勢——起身沿路線走（`walk` 動作、胸前拿一份文件）、到同事座位旁面向對方站著點頭交接（文件在交接中途放下）、空手走回。走完或被中止時，一律放回座位、恢復朝向與依狀態的姿勢。
- `agents/courier.ts`（純函式）：`along`（沿折線走指定距離）與 `courierState(route, 經過時間)` → 階段（去程 / 交接 / 回程 / 完成）、位置、朝向、是否拿文件。路線與時間直接用 T-407 的 `routeFor`（加上交接時要面向的點：同事的椅子或審批桌），結束時間與佇列一致到毫秒。
- **驗收條件**：新的執行開始（`AGENT_RUN_STARTED`）→ 導演中止走路 → 下一幀人物回到座位（位置、朝向、文件隱藏、姿勢不再是走路）。

### 驗證
- `courier.test.tsx`：5 個通過——時間軸（沿路線的位置與朝向、交接時面向同事且文件半途放下、空手回程、單程走路停在目標）；**整條真實鏈路**（store 事件 → 導演 → 佇列 → 人物，時間由測試控制）：剛發生的交接事件讓人物離開座位、走路、拿著文件，在分析師座位旁交接；**接著新執行開始，人物立刻回到原座位與朝向**；不打斷時走完也回到座位。
- 第一次跑時，走完那一刻還差不到 1 毫秒沒「完成」（路線時間四捨五入），改為回程以佇列的結束時間為準。
- 真實瀏覽器（測試環境跑一次 EchoWorkflow，分析師回覆放慢）：依序截圖——Rae 拿著文件起身、沿前方走道走、在 Ana 旁面向她交接、空手走回。
- web 共 186 個測試、event-schema 8 個通過；`typecheck`、`lint`、`check-assets`、`next build`、`make e2e`（5 個）以結束碼確認通過；開發伺服器 `/office` 無錯誤。

## T-407 · Animation Director 與 CueRunner

### 做了什麼
- `visual/cues.ts`、`visual/director.ts`：**事件 → 動畫提示**的純函式 `cuesFor`（04 §4 的表）：
  - 帶交接的 `AGENT_RUN_COMPLETED`、帶 `unlocks` 的 `TASK_SUCCEEDED` → 走到下一個角色的桌子、拿著文件、再走回來（下一步是人工時改走審批桌）；
  - `APPROVAL_REQUESTED` → 走到審批桌再回來；
  - 最終的 `AGENT_RUN_FAILED` / `AGENT_RUN_ABORTED` → 紅色閃光 1 秒（會重試的不閃）；
  - `CYCLE_STARTED` → 執行長螢幕警示 2 秒；
  - `AGENT_RUN_STARTED` → 中止該代理的走路（狀態優先於動畫）；
  - 思考 / 工作 / 檢查 / 等待 / 暫停等不是提示，姿勢由對照表決定。
- **每位代理的提示佇列** `CueQueue` 與合併規則：同一目標已排隊或正在走，不再加入；新的執行開始時立即中止走路並清空排隊；**超過 10 秒的事件不產生提示**（重連補回大量歷史事件時只更新狀態）；每人最多排 4 趟；走路依序一趟一趟，閃光與螢幕警示是疊加效果、立即開始並可與走路同時；同一效果再來一次就重新計時；分頁隱藏後恢復時直接快轉到期。
- `visual/CueRunner.tsx`：`CueDirector` 訂閱 store，只把「沒看過的新事件」交給導演（初次快照與切換公司不產生提示）；`useFrame` 推進佇列；`routeFor` 依平面圖算出走路路線與時間（每秒 1.4 公尺、來回、交接停留 1.2 秒）——T-408 的 Courier 會照這條路線實際走。
- 效果的顯示：閃光讓該代理的桌燈變紅閃、螢幕警示讓螢幕變琥珀；**審批桌新增一盞燈**，只要有人在等審批就琥珀閃（依狀態而非提示，所以重新整理後仍正確）。
- 發現：審批事件的 `agent_id` 是空的（真實紀錄中，請求者在 `actor`）。導演改用「`agent_id`，否則取身為代理的 actor」，不改後端。

### 驗證
- `director.test.ts`：15 個通過——用真實紀錄的事件逐條對照 04 §4 的表（交接、解鎖、審批請求、最終失敗 / 中止會閃而重試不閃、新執行中止走路、新週期警示執行長、姿勢事件不產生提示）；**10 秒 TTL 的邊界**、整段歷史以一分鐘後的時間重播不產生任何提示；佇列規則（同目標不重複、依序、上限、中止、效果並行與重新計時、隱藏一小時後快轉、無處可去的走路略過）；`CueDirector`：快照與舊事件不產生提示、剛發生的完成事件產生走路；路線（到同角色同事的桌旁、時間公式、審批桌、沒有座位時沒有路線）。
- `indicators.test.tsx` 新增：閃光蓋過桌燈變紅、有人等審批時審批桌燈變琥珀。
- 真實瀏覽器（測試環境、打開審批開關）：審批桌的燈在寫手等審批前是暖白、之後是琥珀。走路本身在 T-408 呈現。
- web 共 181 個測試、event-schema 8 個通過；`typecheck`、`lint`、`check-assets`、`next build`、`make e2e`（5 個）以結束碼確認通過；開發伺服器 `/office` 無錯誤。

## T-406 · 螢幕、桌燈與頭頂標籤

### 做了什麼
- `visual/tracker.tsx`：**整個場景共用一個狀態追蹤器**——訂閱 store（加上每秒重讀處理 display_until），算出每位代理的視覺狀態，有任何改變時 `version` 加一；在畫面迴圈最先執行（`useFrame` 優先序 -1）。螢幕、桌燈、標籤都讀它，不各自重算。
- `agents/roster.ts`：人員名單與座位分配抽成共用的 `useRoster()`（名單字串 selector，只在有人加入 / 離開 / 改名時重繪），另提供「座位 → 代理」對照。

## T-401 · OfficeCanvas

### 做了什麼
- 新頁面 **`/office`**（Dashboard 右上角「辦公室」連結）：標頭有「自動 / 3D / 2D」切換（寫在網址 `?view=3d|2d`，可分享）、Dashboard 連結、連線狀態；下方是辦公室畫布。
- `office3d/OfficeCanvas.tsx`（3D 層唯一對外的元件，ESLint 規則已限制）：
  - **選擇 3D 或 2D**（`capabilities.ts`，純函式）：沒有 WebGL 2 一律 2D（就算選了 3D）；窄螢幕（≤ 768 px）自動用 2D，但可手動切到 3D；偵測用的 WebGL context 用完立即釋放。只在瀏覽器端偵測一次，伺服器端渲染時先顯示空白區。
  - **動態載入**：WebGL 部分（`Canvas3D.tsx`）用 `next/dynamic`（`ssr: false`）只在選了 3D 時才下載。
  - **DPR** `[1, 1.5]`；**分頁隱藏時停止繪製**（`frameloop="never"`）。
  - **WebGL context 遺失**：顯示「3D 暫停」與「重新建立 3D」「改用 2D 看板」兩個按鈕；**不自動重試**。重新建立 = 換一個新的畫布（新的 context）；瀏覽器自己恢復 context 時提示自動消失。
- `Canvas3D.tsx` 目前只有相機、燈光與地板（暖色粉彩，D-008）；房間、桌椅與人物從 T-402 開始。
- `fallback/OfficeBoard2D.tsx`：暫時的 2D 看板，列出代理的名字、角色、狀態；T-410 再依視覺對照表做完整版。

### 決策：React 釘在 19.2.8（D-009）
安裝 React Three Fiber 9.7（最新穩定版）時出現 peer 警告：它只支援 `react <19.3`，並內建對應 React 19.2 的 reconciler，而專案原本用 19.3.0。錯配是未經測試的組合，所以改用 19.2.8（同一大版本內的小降版，Next 16.3.5 支援），等 R3F 支援 19.3 再升級。改版後原有全部測試與階段 3 的兩個驗收測試都通過。

### 過程中的問題
- 安裝套件時 pnpm 重整 `node_modules`，開著的開發伺服器（3000）因此找不到套件、出現一連串錯誤；重啟開發伺服器後恢復正常。**之後安裝套件要順手重啟開發伺服器。**
- Playwright 的 CSS 選擇器 `[data-office-mode=3d]` 不合法（屬性值以數字開頭必須加引號）；Next 的路由播報器也是 `role="alert"`，測試改以文字找「3D 暫停」提示。

### 驗證
- `office-canvas.test.tsx`：13 個通過——3D / 2D 選擇的完整對照、`?view=` 解析、WebGL 2 偵測（含釋放偵測用 context、偵測拋錯）、無 WebGL 顯示 2D 與原因、窄螢幕、分頁隱藏停止繪製、context 遺失的提示與**只在按下按鈕時重建**、瀏覽器自行恢復。
- **真實瀏覽器**（`e2e/office.spec.ts`，Playwright + 測試環境，本機 Chrome）：3 個通過——桌機得到 WebGL 2 畫布且 context 正常；用 `WEBGL_lose_context` 真的讓 context 遺失 → 出現提示 → 按「重新建立 3D」得到新的可用 context；`?view=2d`、手機寬度（390 px）、停用 WebGL 2 的瀏覽器都顯示 2D 看板（列出 3 位代理）。我看過截圖：3D 畫面有打光的地板與暖色背景，連線狀態「即時」。
- CI 的 Linux 環境沒有 GPU：Playwright 在 CI 加上 SwiftShader 參數（軟體 WebGL）。
- web 共 110 個測試、event-schema 8 個通過；`typecheck`、`lint`、`next build`（新路由 `/office`）、`gen-api:check` 以結束碼確認通過；`make e2e` 5 個（辦公室 3 個 + 階段 3 驗收 2 個）通過。
- 開發伺服器重啟後 `/office` 編譯無錯誤、主控台無錯誤（停在權杖畫面）。
